# 割り勘アプリ 解析メモ

作成日: 2026-08-02

## 1. 一言でいうと

**飲み会などの立て替え金を精算する、個人利用向けのローカル Web アプリ。**

参加者と支払い額を入力すると「誰が誰にいくら払えばいいか」を送金回数が最小になるように自動計算し、支払い済みチェックと履歴保存ができる。スマホ幅（max-width 480px）前提のシンプルな UI。

## 2. 技術構成

| 項目 | 内容 |
|------|------|
| 言語 / FW | Python + Flask（単一ファイル `app.py`、約 220 行） |
| テンプレート | Jinja2（`templates/` 配下 7ファイル、`base.html` を継承） |
| CSS / JS | フレームワーク不使用。CSS は `base.html` に直書き、JS は品目モード画面のみバニラ JS |
| データストア | DB なし。`data/sessions.json` に JSON 配列で保存（最大5件） |
| 状態管理 | Flask の `session`（Cookie ベース）にウィザードの途中状態を保持 |
| 依存管理 | `requirements.txt` なし。Flask のみ手動インストール前提 |
| 起動 | `python app.py`（`debug=True`）／Windows は `start_warikan.bat` でブラウザも自動起動 |
| テスト | なし |

外部 API 通信・認証・ユーザー管理は一切なし。完全にローカル単独動作。

## 3. 画面フロー

```
  /  (トップ: 履歴一覧)
   │
   ├─ 「＋ 新しい割り勘を始める」 → /new (session クリア)
   │                                  ↓
   │                              /step1  タイトル・人数(2〜20)・モード選択
   │                                  ↓
   │                              /step2  ┬─ simple → step2_simple.html
   │                                      └─ items  → step2_items.html
   │                                  ↓  （ここで精算計算が走る）
   │                              /step3  精算結果・支払いチェック・保存
   │
   └─ 履歴クリック → /history/<id> → session に復元 → /step3 へリダイレクト
      🗑ボタン      → /history/<id>/delete
```

### 2つの入力モード

- **シンプルモード** (`mode="simple"`)
  「名前 + 実際に払った金額」を人数分入力するだけ。サーバー側でそのまま集計。

- **品目別モード** (`mode="items"`)
  先にメンバー名を入力 → 「品目名・金額・支払った人」を JS でリストに追加していく。
  追加した品目は hidden input（`item_name_N` / `item_amount_N` / `item_paid_by_N` + `item_count`）としてまとめて POST される。
  サーバー側で品目を支払者ごとに合算し、シンプルモードと同じ `members` 形式に正規化してから計算する。

  → **つまり品目モードは「支払い額の入力方法が違うだけ」で、精算ロジックは共通。**
  品目ごとに「誰が消費したか」を分ける機能はなく、割り勘は常に**全員均等割り**。

## 4. 中核ロジック: `calculate_settlements()`

[app.py:28](../app.py) — このアプリの心臓部。貪欲法（greedy）による最小送金回数の精算。

```
1. total = 全員の支払い額の合計
2. per_person = total / 人数              ← 常に均等割り
3. 各人の balance = paid - per_person
     balance > 0 → 受け取る側（creditor）: 立て替えすぎ
     balance < 0 → 支払う側（debtor）    : 払い足りない
4. creditor を金額降順、debtor を金額昇順（=絶対値降順）にソート
5. 先頭同士をマッチングし min(受取残, 支払残) を送金として確定。
   残高が 0 になった方のポインタを進める。両方尽きるまで繰り返す。
```

返り値は `(total, per_person, settlements)`。`settlements` の各要素は
`{"from": 支払う人, "to": 受け取る人, "amount": 金額, "paid": 支払い済みフラグ}`。

この手法により、送金回数は最大で「人数 − 1」回に収まる。

## 5. データモデル

### セッション（Cookie）に持つキー
`title` / `count` / `mode` / `members` / `items` / `total` / `per_person` / `settlements` / `editing_id`

### `data/sessions.json` の1エントリ

```json
{
  "id": "8桁のuuid断片",
  "title": "飲み会 5/13",      // 未入力時は "割り勘 MM/DD" を自動生成
  "created_at": "2026-08-02",
  "mode": "simple" | "items",
  "members":     [{ "name": "田中", "paid": 5000 }],
  "items":       [{ "name": "ビール代", "amount": 3000, "paid_by": "田中" }],
  "total": 12000,
  "per_person": 4000,
  "settlements": [{ "from": "佐藤", "to": "田中", "amount": 1000, "paid": false }]
}
```

### 保存の挙動（やや独特）

- step3 の「💾 保存」を押して初めてファイルに書き込まれる。この時 `editing_id` が session にセットされる。
- 一度保存された後（= `editing_id` あり）は、支払い済みチェックを切り替えるたびに**自動でファイルへ再保存**される。UI 上も「保存」ボタンが「🏠 トップへ」に変わる。
- 保存時は同一 ID の既存エントリを除去してから先頭に挿入 → **常に新しい順**。`MAX_SESSIONS = 5` を超えた分は切り捨てられる。

## 6. UI / UX の特徴

- スマホ前提の縦1カラム。カード型 UI、角丸 16px、青系アクセント（`#5b8dee`）で統一。
- 絵文字を積極的に使用（💰 🪙 🧾 💸 ✅ 🗑）。
- 支払い済みチェックはトグルすると即 form を submit → 該当行が取り消し線＋グレーアウト。
- 全員の支払い額が同じ場合は「✅ 全員の支払い額が同じです！精算不要です」を表示。
- 履歴削除は `confirm()` で確認あり。

## 7. 気づいた点・注意点

改修時に踏みやすい箇所を列挙。（現状は個人のローカル利用前提なので、実害の有無はスコープ次第）

### 設計上の制約
- **`templates/step2.html` は未使用の残存ファイル。** どのルートからも参照されていない（実際に使われるのは `step2_simple.html` / `step2_items.html`）。削除候補。
- **メンバーの識別子が「名前」文字列。** 同名のメンバーが2人いると `paid_map` で合算されて破綻する。
- **ウィザード状態が全て Cookie に載る。** `members` / `items` / `settlements` を丸ごと session に入れているため、人数や品目数が多いと Cookie の 4KB 制限に当たる可能性がある。
- **ステップの順序を検証していない。** `/step2` や `/step3` に直接アクセスしても弾かれず、その時点の session の中身次第の表示になる（空なら合計 0 円扱い）。
- **端数処理。** `per_person` は割り切れない場合に丸められ、各送金額も `round()` で整数化されるため、送金額の合計と理論値が数円ずれることがある。
- **`len(members)` が 0 だとゼロ除算。** `count` は HTML の `min="2"` でしか守られておらず、サーバー側の検証がない。

### セキュリティ関連（ローカル運用なら低リスクだが、公開するなら要対応）
- `app.secret_key` が `"warikan-secret-key"` でハードコードされている。
- `app.run(debug=True)` のまま（デバッガ経由の任意コード実行が可能）。
- `step2_items.html` の JS が品目名・メンバー名を `innerHTML` にエスケープなしで埋め込んでいる（`${item.name}` 等）→ XSS が成立しうる。

## 8. 拡張するとしたら
